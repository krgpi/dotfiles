# triage-review

PR のレビューコメント（複数の指摘を含むレビューレポートや、レビュアーからの指摘一覧）について、
**各指摘ごとに「対応する／対応しない」をエンジニアリング判断**し、対応分を実装・検証・コミットした上で、
判断結果をレビューコメントに反映し、見送り分の理由を説明する返信コメントを投稿する。

引数「$1」はレビューコメントの URL（`https://github.com/<owner>/<repo>/pull/<N>#issuecomment-<ID>`）または PR 番号。
省略された場合は、現在のブランチに紐づく PR の最新レビューコメントを対象にする。

## 大前提

- **必ず実コードを読んでから判断する。** 指摘文だけで判断せず、参照ファイル・行を開き、本当に問題か検証する。
- **全項目について「対応する／対応しない」の推奨を根拠付きで出し、最終可否は `AskUserQuestion` でユーザーに確認する。** 玉虫色にしない。
- コーディングはプロジェクト／グローバルの `CLAUDE.md` の規約に従う（最小 diff・周囲のコードに溶け込む・コメントは原則書かない 等）。

## ワークフロー

### Step 1: 対象コメントと PR コンテキストの取得

```sh
# コメント本文（URL の #issuecomment-<ID> の数字が <ID>）
gh api repos/<owner>/<repo>/issues/comments/<ID> --jq '.body'
# PR の概要・ブランチ
gh pr view <N> --repo <owner>/<repo> --json title,body,headRefName,baseRefName
```

指摘を項目ごとに分解する。レビューレポート形式（番号付き・重大さ付き・「対応する／対応しない」チェックボックス表を持つもの）の場合は、その表の各行を1項目として扱う。

### Step 2: 各項目を実コードと照合して推奨を作る

項目ごとに参照ファイル・行を `Read` し、次の観点で**対応可否の推奨を決める**。

- **実害があるか**: 実際にバグ・パニック・誤出力を起こすか。それとも理論上のみか。
- **到達可能か**: その不具合経路に現実に到達しうるか（呼び出し元のガード、入力の制御状況などを確認）。
- **現状すでに正しくないか**: 「修正」が現挙動と機能的に等価な書き換えにすぎないなら見送り候補。
- **恒久的な価値か**: 将来の呼び出し追加・リファクタで壊れる「時限爆弾」か、それとも恒真の死んだ条件か。
- **コスト対効果と最小 diff**: 効果に対して diff・フィクスチャ作成コストが見合うか。

各項目について **推奨（対応する／対応しない）＋1〜2文の根拠** を表にまとめて提示する。

### Step 3: 各項目の対応可否をユーザーに確認

**最終判断はユーザーに委ねる。** `AskUserQuestion` で、各指摘につき1問ずつ「対応する／対応しない」を質問する。

- 1問 = 1指摘。指摘が5件以上ある場合は `AskUserQuestion` の1回あたり最大4問の制約に従い、複数回に分けて尋ねる。
- `header` は項目番号や短い識別子（例: `#1 splitsLatinWord`）。`question` に指摘の要旨を入れる。
- 選択肢は2つ（「対応する」「対応しない」）。**推奨する側を先頭に置き、`label` の末尾に「(推奨)」を付ける。**
- 各選択肢の `description` に **Step 2 で出した根拠（推奨理由）** を入れる。推奨しない側にも、なぜそれが次善かを簡潔に書く。
- ユーザーがいずれの項目でも「Other」で自由入力できる点はそのまま活かす（条件付き対応などの指示を拾う）。

ユーザーの回答を最終判断として確定し、以降のステップに進む。

### Step 4: 「対応する」と確定した項目の実装

- 最小 diff で、周囲のコードの命名・構造・イディオムに合わせて実装する。
- コメントは原則書かない（非自明な制約・バグ回避策のみ1行許可）。
- **バグ修正の場合は回帰テストを追加し、可能なら「修正前コードで FAIL・修正後で PASS」を実機確認する**
  （該当箇所を一時的に旧実装へ戻してテスト実行 → 元に戻す、等）。
- ヘルパーに防御ガードを足す場合は、そのコードベースで既に確立された自己防御パターン（入口ガード等）に揃える。

### Step 5: 検証

そのプロジェクトの規約に従いテスト・整形・静的解析を実行し、クリーンであることを確認する。

```sh
# 例（プロジェクトにより異なる）
go test ./<pkg>/... ; gofmt -l <files> ; go vet ./<pkg>/...
```

### Step 6: コミット & プッシュ

- 現在のブランチ（PR ブランチ）にコミットする。`main` 等の保護ブランチにいる場合は先にブランチを切る。
- **コミットメッセージはそのリポジトリの規約を踏襲する**（`git log` で gitmoji・接頭辞などのスタイルを確認）。
- 変更を PR に反映するためプッシュする。

### Step 7: レビューコメントのチェックボックス更新

対象コメントが「対応する／対応しない」チェックボックス表を持つ場合、判断どおりに `- [ ]` → `- [x]` を更新する。

- 各行は左から「対応する」「対応しない」の順。判断に応じて片方だけチェックする。
- 表に重大さ等のチェックボックスを持たない列が挟まる場合があるため、**列インデックスを取り違えない**こと（更新後に各行の状態を必ず検算する）。

```sh
# 編集した本文をファイルに書き出して PATCH する
gh api repos/<owner>/<repo>/issues/comments/<ID> -X PATCH -F body=@<新本文ファイル>
```

チェックボックス表が無い形式のコメントなら本ステップはスキップする。

### Step 8: 説明返信コメントの投稿

PR に返信コメントを投稿する。内容は:

- **対応した項目**: 何を・なぜそう直したか、追加テストが旧コードで FAIL することの確認結果、コミット SHA。
- **見送った項目**: 見送り理由を明確に（例: 現状すでに正しい／到達不能／恒真の死んだ条件／コスト過大）。
- 末尾に「防御的に明示したい等の要望があれば追加対応する」旨を一言添える。

```sh
gh api repos/<owner>/<repo>/issues/<N>/comments -F body=@<返信本文ファイル> --jq '.html_url'
```

## 注意事項

- コミット・プッシュ・コメント投稿・チェックボックス更新といった外向きの副作用を伴う操作は、判断結果を提示して合意を得てから実施する（ユーザーが「やっといて」と明示した場合はそのまま進めてよい）。
- 日本語・改行・記号を含む本文は一時ファイル（`mktemp`）に書いてから `-F body=@<file>` で渡す（シェル経由のエスケープ崩れを避ける）。
- 判断は是々非々で行い、「レビュアーを満足させるため」だけの無価値な変更（恒真の死んだ条件追加・機能的に等価な書き換え）はしない。見送る場合は理由で説得する。
