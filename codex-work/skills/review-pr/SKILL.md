# review-pr

PR を複数の観点から自分でレビューし、確信度ラベル（`[must]`/`[should]`/`[imo]`/`[q]`）付きの指摘をまとめ、承認後に GitHub へインラインコメントとして投稿する。

対象PRの番号またはURLはユーザーの依頼内容から読み取る。省略時は現在のブランチに紐づくPRを対象にする。

## 大前提

- **自分の初見の判断を鵜呑みにしない。** 特にランタイム安全性に関わる指摘は、実装コード（バリデーション層・呼び出し経路）を読んで裏取りする。観点ごとに矛盾する結論が出た場合は実装を読んで裁定する。
- **GitHubへのコメント投稿はユーザーの明示的な承認後に行う**（「投稿して」等の明示指示があれば省略可）。

## ワークフロー

### Step 1: PR情報と全文diffの取得

```sh
gh pr view <番号> --json title,body,files,additions,deletions,baseRefName,headRefName
gh pr diff <番号>
```

- PR本文・コミットメッセージから意図と「意図的にスコープ外」とされている事項を把握する。
- 現在のworktreeがPRブランチと一致するか確認する（`git diff <PRブランチ> -- <対象ファイル>`）。不一致ならローカルファイルはbaseブランチの状態として扱う。

### Step 2: コンテキスト収集

- 変更ロジックと同種のパターン（同じ値をDBに保存/比較する別usecase等）をgrepで横断的に洗い出す。
- 変更箇所の呼び出し元（バリデーションの有無、型保証がランタイムでも成立するか）を確認する。
- 書き込み側だけでなく対になる比較・読み取り側のコードも見て整合性を確認する。

### Step 3: 観点ごとに自分で順にレビューする

diffが小さくても、以下の観点を一つずつ確認する。並列サブエージェントには投げられないので、観点ごとに集中してチェックし直すつもりで進める。

- **常時**: 一般的なコードレビュー（バグ・ロジック誤り・設計・命名・既存パターンとの整合性）
- テストファイルの変更があれば: テストカバレッジ（新規ロジックに対する境界値・異常系のテストがあるか）
- エラーハンドリング（catch/フォールバック/リトライ等）の変更があれば: silent failure（エラーの握りつぶし、不適切なフォールバック）
- 新規/変更された型があれば: 型設計（不変条件の表現、カプセル化）
- コメント・docstringの追加/変更があれば: コメントの正確性（コードとの乖離、將来陳腐化しやすい記述）
- **常時**: 層責務分離（アーキテクチャの層（UI層/ロジック層等）を越えて責務が漏れていないか。UI専用の判定・ラベルが下位層に紛れ込む、権限チェックが本来行うべき層で実施されていない等）
- **常時**: 秘密情報の露出（クライアントに届くコード・ログ出力・エラーメッセージに秘密情報（APIキー、トークン、個人情報）が含まれていないか）
- 非同期処理（API呼び出し・フォーム送信等）の変更があれば: ユーザーフィードバック（成功/失敗が画面に反映される実装になっているか。処理自体は成功するが結果が伝わらない実装漏れ）
- **常時**: プロジェクト固有の不変条件（プロジェクトのAGENTS.md/CLAUDE.md等に明記された最優先制約（セキュリティ、データ分離等）に違反していないか）
- **常時**: シンプルさ・非冗長性（同じロジック・文字列・設定値が複数箇所に重複していないか、要件に対して過剰な抽象化・複雑な実装になっていないか）
- **常時**: 単一情報源（SSoT）（同じ情報を複数の場所で個別に保持・管理していないか。派生できる値を別途State/変数として持つ等）
- **常時**: 疎結合（モジュール間の依存が不必要に強くなっていないか。本来不要な内部実装への依存、循環依存等）
- TypeScriptファイルの変更があれば、以下も確認する:
  - **ユーティリティ型の活用**: `Pick`/`Omit`/`Partial`/`Record`等で表現できる型を手書きで重複定義していないか
  - **any型の使用**: `any`を使っている箇所は`unknown`+型ガードで代替できないか
  - **冗長な型ガード**: 型で既に保証されている値に対して不要な型ガード・再検証をしていないか
  - **アサーションの濫用**: `as`によるキャストや非nullアサーション（`!`）で型安全性を回避していないか、より安全な書き方（型ガード等）がないか
  - **網羅性チェック**: union型に対するswitch/if分岐が、メンバー追加時にコンパイルエラーで検知できる形（`never`を使った網羅性チェック等）になっているか
  - **理由のないoptional**: `?`を付けたフィールド・引数が、なぜ任意なのか自明でない設計になっていないか
  - **型定義の重複**: 同じ形状の型を複数箇所で個別に手書きしていないか（既存の型・ユーティリティ型で一本化できないか）
- バックエンド（API/サーバー処理）の変更があれば、以下も確認する:
  - **認可チェックの抜け漏れ**: エンドポイント/操作ごとに権限確認が行われているか
  - **冪等性**: リトライ・二重送信時に重複処理（二重課金、二重作成等）が起きないか
  - **トランザクション境界**: 複数の書き込みが原子性を保っているか、一部だけ成功する中途半端な状態が起きないか
  - **N+1クエリ・非効率なDB呼び出し**: ループ内で個別クエリを発行していないか、一括取得で解消できないか
- フロントエンド（UI）の変更があれば、以下も確認する:
  - **非同期状態のハンドリング**: ローディング中・エラー時の表示漏れがないか
  - **不要な再レンダリング**: 依存配列の誤り、メモ化漏れによる無駄な再計算・再描画がないか
  - **XSS対策**: `dangerouslySetInnerHTML`等で未サニタイズの値を出力していないか
  - **アクセシビリティ**: キーボード操作・フォーカス管理が欠落していないか

各観点について、Step 2 で得たコンテキストを踏まえたうえで「該当なしならその通りでよい、無理に問題を作らない」姿勢で確認する。

### Step 4: 集約してユーザーに提示

- Critical/Important/Suggestions ではなく確信度ラベルで分類する: `[must]`（確実に直すべき欠陥）/ `[should]`（推奨だが必須でない）/ `[imo]`（自分の見解・判断）/ `[q]`（ユーザーの判断が要る問い）。
- スコープ外だが関連する発見（同型バグが別ファイルに残っている等）は明示的に分けて報告する。
- 前置き・相槌なしで結論から。同じ主張の言い換え水増しをしない。「やって当然の確認」は書かず、副次的影響・関連issue/PRとの紐付け・見落としやすい設計判断を優先する。
- 指示がない限り「次にやること」のまとめは書かない。指摘を列挙して終える。

### Step 5: GitHubへの投稿(ユーザー承認後)

```sh
gh api repos/<owner>/<repo>/pulls/<番号>/files --jq '.[] | {filename, patch}'
```

で実際のdiff hunkと行番号を確認してから組み立てる（推測で行番号を数えない）。

- インラインコメントはdiffに含まれる行にしか打てない。対象ファイルがPRの差分に含まれない場合はreviewの`body`（全体コメント）に回す。
- コメント本文の冒頭に確信度タグ（`[must]`等）を付ける。
- 一時JSONファイルに書き出し、以下で投稿する（シェルエスケープでの直書きは避ける）。

```sh
gh api --method POST repos/<owner>/<repo>/pulls/<番号>/reviews --input <ファイル>
```

- `event` は基本 `COMMENT`（本人が自分のPRをレビューする場合、APPROVE/REQUEST_CHANGES は権限エラーになりうる）。

## 注意事項

- GitHubへのコメント投稿は外向きの副作用を伴う。ユーザーの明示的な承認を得てから実施する。
- 日本語・記号を含む本文は一時ファイルに書いてから `--input`/`-F body=@<file>` で渡す（シェル経由のエスケープ崩れを避ける）。
