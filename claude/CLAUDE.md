# Global Instructions

## 指示の記録方法

- ユーザーから受けた恒久的な指示・好み・ルールは、Claude Code の恒久メモリ機能には書かず、このリポジトリで管理する CLAUDE.md（グローバルは `claude/CLAUDE.md`、プロジェクト固有は各リポジトリの CLAUDE.md）に記述する
- 適切なセクションに最小限の差分で追記する

## 自動で使用するスキル

以下のスキルは、ユーザーが明示的に呼び出さなくても、状況に応じてプロアクティブに使用すること。

### x-search
- 技術トピックに対するコミュニティの反応・評判を調べたいとき
- 最新のトレンド、障害情報、リアルタイムの話題を把握したいとき
- ライブラリやツールの実際のユーザー体験・評価を知りたいとき
- 使い方: `Skill` ツールで `skill: "karaage-tools:x-search"`, `args: "<検索トピック>"` を呼び出す

### mk-pr
- PRを作成するときは必ずこのスキルを使う（組み込みのPR作成フローではなくこちらを優先）
- 使い方: `Skill` ツールで `skill: "karaage-tools:mk-pr"`, `args: "<ベースブランチ名>"` を呼び出す

### debug-ui
- UIのスタイリング・レイアウト問題をブラウザ上で診断したいとき
- CSSのレイアウト崩れ、レスポンシブ対応の確認が必要なとき
- ユーザーが「レイアウトがおかしい」「崩れている」「はみ出す」「スタイルが当たらない」などの表現を使ったとき
- Chrome拡張のMCPブラウザツールが利用可能な場合のみ使用する
- 使い方: `Skill` ツールで `skill: "karaage-tools:debug-ui"`, `args: "<問題の説明 or URL or CSSセレクタ>"` を呼び出す

### save-report
- Claudeが調査結果や回答を生成した後、ユーザーが「保存して」「レポートにして」「Obsidianに残して」などと依頼したとき
- 長い調査や分析の会話が一段落したとき、ユーザーに保存を提案してもよい
- レポート内の記述にはできるだけWeb上のソース（URL）を根拠として明示すること
- 新しいフォルダを作成せず、Obsidian vault内の既存の適切なフォルダ（1階層まで）を選択して配置すること
- 使い方: `Skill` ツールで `skill: "karaage-tools:save-report"`, `args: "<トピック or タイトル>"` を呼び出す

### pr-review-toolkit:review-pr
- PRが未作成・未Pushでも、ローカルのmainとのdiffを対象にレビューを実行する
- `gh pr view` が失敗した場合は `git diff main...HEAD` を使う

### mock-ui
- ユーザーが「UIのキャプチャ」「スクリーンショットを作って」「モックアップ画像が欲しい」「LP用の画像」などUI画像の生成を依頼したとき
- アプリを起動せずにUI画像が必要な場合
- 使い方: `Skill` ツールで `skill: "karaage-tools:mock-ui"`, `args: "<生成したい画面の説明>"` を呼び出す

## コード生成のルール

- コードにコメントを書かない。プロジェクトの CLAUDE.md で明示的に指定がある場合のみ例外
- ただし「なぜそうするのか」が非自明な場合（隠れた制約、特定バグへの回避策、読者を驚かせる挙動）は1行のみ許可
- diff はなるべく小さく保つ。全面リライトや無関係な整形はせず、必要最小限の箇所だけを変更する
- 既存コードのパターン（命名・構造・スタイル・イディオム）に従い、周囲のコードに溶け込むように書く

### ダミー個人情報のルール（スクショ・モックアップ・サンプルデータ全般）
- **名前**: 実在しないことが明らかな架空の名前を使う（例: 空野はるか、星見ゆう、風間そら）。実在しうる平凡な名前は避ける
- **メールアドレス**: RFC 2606 予約済みドメインのみ使用（`example.com`, `example.org`, `example.net`）
- **電話番号**: 明らかにダミーとわかる番号（例: 000-0000-0000）
- **住所・その他**: 実在しない架空のものを使う

### 判断基準
- WebSearchで十分な場合はWebSearchを優先する
- X検索はリアルタイムの反応・トレンド・障害情報など、SNS特有の情報が必要なときに使う
- PR作成時は常にmk-prスキルを使う
- 複数のソースを組み合わせて精度を上げることを推奨する
- UI/CSSの問題報告がありMCPブラウザツールが利用可能ならdebug-uiを使う
- 長い調査・分析が一段落した後、ユーザーに「Obsidianに保存しますか？」と提案してもよい
- UIモックアップ画像の生成依頼があればmock-uiスキルを使う。アプリのソースコードからデザインを読み取りPlaywrightでPNG化する
